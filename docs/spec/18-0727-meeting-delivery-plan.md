# 2026-07-27 会议闭环与 SKU 标准化实施计划

状态：P0 已完成并经受保护 PR 合并；P1/P2 等真实业务输入、机器授权与 UAT
依据：`AI notes_ 供应链系统会议 July 27,2026 on Jul 27, 2026.pdf`、现行 PRD、`docs/spec/CURRENT.md` 与代码/数据库契约。

## 1. 目标与边界

本轮不重建系统，只补齐能闭合真实经营决策的最小链路：

1. 将样品、赠品、试用装、内用货与正常销售 SKU 分开统计，但它们仍属于库存真相，不能从账本或库存总量中删除。
2. 统一 SKU 可识别名称；现行商家编码永久保留，未来新建/替代 SKU 可使用 S1 前向标准；
   旧码与外部码继续通过别名表解析。
3. 将效期详情页与经营驾驶舱统一为同一套七段位。
4. 补货最晚下单日同时考虑生产与物流/调拨交期，并明确缺失数据。
5. 复用现有 ABC/XYZ、库存分析、销售事实、订单与委外闭环，不制造第二套口径。
6. 为聚水潭、飞书、用友保留治理过的集成边界；没有机器凭证、权限和 UAT 证据时不伪造“已接通”。

## 3. SKU 标准化契约

### 3.1 永久身份

- `skus.code` 继续使用现行商家编码，是不可随展示名称变化的稳定主码。
- 历史码、外部系统码和替代码进入 `aliases(alias_type='sku_code')`，不建立纯数字第二主码。
- SKU 合并、拆分或换码不得由相似度算法自动执行；只能给出候选和证据。
- 本轮新增用途分类不会改变库存、订单、BOM 或台账外键。
- 未来新建/替代 SKU 在页面留空编码时，由服务端按
  `S1-来源-类型-六位全局流水-两位校验码` 同事务原子取号；staging 与历史导入不强制换码。
- 人用规则与操作示例见 [`19-SKU编码标准-S1.md`](19-SKU编码标准-S1.md)。

### 3.2 可识别标准名称

标准名称按非空片段顺序组成：

`品牌 + 渠道 + 产品简称 + 版本 + 规格`

规则：

- 产品简称最多 10 个 Unicode 字符；中文、数字和必要拉丁字符均可保留。
- 相邻重复片段只保留一次，空片段跳过。
- 建议名称由服务端根据当前主档重新生成，客户端不能提交任意“自动结果”。
- 采用建议只改展示名称，不改 SKU 码、SPU、BOM、库存或历史单据。
- 缺品牌或产品简称时只能标记“资料不足”，不能自动采用。

### 3.3 商业用途

用途取值：

- `unclassified`：历史数据尚未确认；
- `retail`：正常销售；
- `sample`：样品；
- `gift`：赠品；
- `tester`：试用/测试装；
- `internal`：内部使用。

历史数据默认 `unclassified`，避免把样品误判为销售品。经营无动销/滞销默认仅统计
`retail` 与 `unclassified`，并单独披露未分类库存 SKU 数；总库存继续包含所有用途。

## 4. 写路径契约

### 4.1 采用标准名称

- 触发：PMC 或管理员在 SKU 工作台明确点击采用。
- 授权：服务端重新读取当前用户、当前 SKU、品牌和渠道。
- 前置状态：SKU 存在，品牌和产品简称齐全。
- 幂等：当前名称已等于建议名称时返回当前结果，不重复制造审计噪声。
- 原子效果：更新 `skus.name` 与一条 `audit_logs` 同事务提交。
- 冲突：若主档在页面打开后变化，以服务器当前字段重新生成；不接受客户端传入的建议名。
- 回退：普通受审计的 SKU 编辑可恢复旧名称；历史单据不受影响。

### 4.2 物流交期维护

- 物流/调拨交期作为 `sku_params` 的独立字段，不覆盖生产周期。
- 总供应周期 = 常规生产周期 + 已维护的物流/调拨周期；未维护物流周期时按 0 处理并披露缺失。
- 更新 SKU 与物流交期必须同事务审计；不得在补货引擎中写死渠道假设。

## 5. 红队结论

| 风险 | 结论与控制 |
|---|---|
| 批量换码破坏历史关联 | 拒绝；主码冻结，外部码走别名 |
| 从名称自动猜样品 | 拒绝；只提供显式分类和待确认状态 |
| 把样品排除出库存 | 拒绝；只在经营动销分析中分层 |
| 自动合并重复 SKU | 拒绝；完整联结候选 + 人工裁决 |
| 用“全渠道”掩盖缺失平台 | 拒绝；显示渠道覆盖和数据截至日期 |
| 将生产周期覆盖成总交期 | 拒绝；生产、物流、总周期三者分别展示 |
| 为每个会议点新建页面 | 拒绝；复用 SKU、效期、分层、库存、补货和工作台 |
| 使用用友网页登录口令做 API 集成 | 拒绝；只接受企业开放平台机器凭证和已批准权限 |
| 连接器直接写正式账 | 拒绝；外部事实先 staging、校验、对账、人工/策略放行 |

## 6. 执行顺序

### P0：已完成（2026-07-30）

1. SKU 用途、渠道、简称与标准名建议/采用闭环。
2. 效期详情七段位统一。
3. 物流交期进入供应参数和补货总周期。
4. 驾驶舱样品/未分类口径修正与披露。
5. S1 前向编码生成、校验、原子取号、UI 说明与历史码兼容。
6. 对应迁移、单元/服务/架构测试、文档和 UI。
7. GitHub `main` 保护：必须通过静态检查、全量测试、生产容器和 PostgreSQL 迁移契约。

完成证据：上述 1–7 均已进入 `main`；当前 38 个迁移、1,730 个测试全绿，生产容器与真实
PostgreSQL 契约通过。GitHub Pro 的 `main` 强制 PR、线性历史、会话解决和四项 required
checks；S1 交付由 PR #4 合并，未绕过保护。

### P1：凭证或业务数据到位后

1. 导入 7 月末样品盘点清单，经 staging 预览后分类。
2. 指定 2 个试点产品、业务/供应链/财务各 1 名试点用户。
3. 聚水潭库存/订单/销售 UAT，对账通过后再排程。
4. 飞书自建应用的 App ID/Secret、权限和目标会话完成后启用通知/登录 UAT。
5. 用友企业开放平台创建机器应用，取得 API 目录、租户/账套、客户端凭证和沙箱后实现适配器。

### P2：试点证据驱动

1. 根据两个产品的真实流转反馈修正审批、异常和角色导航。
2. 日库存快照覆盖稳定后，把周转率从“当前库存近似”升级为日均库存。
3. 渠道与仓库映射经业务确认后，启用跨仓调拨时效与渠道服务水平。

## 7. 外部集成最小资料清单

### 聚水潭

- 开放平台应用的 App Key、App Secret、授权 Token；
- 商户/店铺范围、接口权限、出口 IP 白名单；
- 订单、库存、销售接口清单与增量游标；
- 沙箱或脱敏商户、对账基准日、失败重放联系人。

### 飞书

- 企业自建应用 App ID、App Secret；
- 登录回调域名、机器人/消息权限、需要的 API scopes；
- 目标 `chat_id` 或 webhook、应用可见范围；
- UAT 用户与授权撤销/令牌轮换方案。

### 用友

- 企业开放平台机器应用，不使用个人网页登录凭证；
- 租户、账套、组织、环境（沙箱/生产）标识；
- Client ID/Secret 或平台规定的签名材料；
- SKU、库存、订单、采购、财务凭证的具体 API 目录与字段样例；
- 幂等键、分页、增量时间戳、限流、错误码和回调重试约定。
