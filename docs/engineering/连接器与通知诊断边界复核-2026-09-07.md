## 问题与改动

- JST/Yonyou 的 HTTP 传输层原本已拒绝复制网络原始异常，但业务信封 `msg/message`
  仍进入 API Error（用友还保存在 detail 属性）。现只保留代码、受控契约名和固定中文恢复提示；
  非法用友 code 归 unknown，不把它作为第二个任意文本出口。移除原文构造参数及 detail。
- 用友拒绝不安全端点时不再回显 URL，白名单和 DNS 检查不变。
- 五条同步失败出口和 failImportJob 复用存储诊断净化；保留 SQLSTATE、应用生成的
  完整性说明、缺失 ID 和恢复指引，不调用任意异常对象的 getter/toString。
  数据库原始 SQL/绑定值不会进入失败 staging 或下载的拒收文件。
- 飞书任意抛出值（包括 null、undefined、字符串、自定义 getter）不再使 catch 二次崩溃。
  保存通知编号及“失败或结果未确认”，业务错误保留数值码；后续通知继续处理，租约释放、
  失败重试和“不跨渠道回退”保留。sent 仍只在发送调用成功后写入。
- 管理员错误列表和运维最近错误，对历史 path 也使用统一净化投影；不改写或删除历史记录。

## 限制与后续

这是诊断边界修复，不是外部平台已授权、数据全量可读或业务UAT完成。
净化器不能识别任意无标签个人信息；新提供方必须在构造异常前拒绝原始上游文字，
不能仅依赖正则。本轮没有穷尽所有本地解析器把源字段嵌入报错的路径。
历史凭据处置、seed/客户端错误边界、能力台账失效引用、全站小屏宽表、真实角色使用及受控交付仍待办。
