目标：把简道云、聚水潭、用友的数据真正变成决策的输入，而不是停在「已同步」。
本文先说实测到的事实，再说瓶颈在哪，最后给分阶段的执行清单——第一阶段已经落地。

## 2. 瓶颈：不是数据不够，是身份对不上

外部需求信号、退款驱动、履约缺口、渠道贡献……所有分析都只能作用于**已映射到系统 SKU** 的那部分。实测：

| | 平台 SKU 数 | 占支付金额 |
|---|---:|---:|
| 经对照表 → 商家编码 精确映射 | 573 | **46.7%** |
| 在对照表里、有条码但无编码（条码认领队列 291 条待处理） | 282 | ~4.7% |
| **根本不在对照表里** | **1,217** | **44.2%** |

销量最大的品全在最后一行：NING 补水睡眠面膜（¥161 万 + ¥139 万 + ¥69 万）、清洁泥膜（¥108 万）、
DEVIANCE 氨基酸洗面奶（¥76 万）…… 既有的身份控制塔只能看见对照表里的行，对这一半营收是盲区。

**所以第一阶段不是再接更多数据，而是先让现有的一半营收能归到 SKU。**

## 3. 第一阶段（已落地）：营收排序的身份缺口 + 第二条身份桥

### 做了什么

1. **读模型 `platform-sku-identity-gap`**（`/api/report/platform-sku-identity-gap`）
   - 每个平台 SKU：4 个月支付金额、件数、退款、最近售出日、身份状态
     （已映射 / 已认领 / 对照表无编码 / 条码待认领 / 不在对照表），**按金额倒序**；
   - **建议候选**：按店铺推断品牌，用规格（`净含量:220g` → `220g`）与名称词元和系统成品比对打分，
     最多 3 个，只建议不裁决；
   - 给出「若采纳全部建议，金额覆盖率会到多少」，让业务看到投入产出。
2. **第二条身份桥**：业务在决策工作室「平台身份覆盖」标签一键认领 →
   `sku_identifiers(kind=external, scope=JIANDAOYUN:TMALL, value=店铺|平台SKU)`，
   写守卫回查、同事务审计、幂等、冲突 409（`/api/master/sku/platform-claim`）。
3. **外部需求信号**在对照表给不出唯一归属时改走这条桥——认领一个，覆盖率立刻上升，
   滚动需求简报、退款驱动、履约对比全部受益。
4. 读模型随连接器同步重建，并在认领后主动刷新；绑定精确批次 + 认领版本。

### 纪律（与既有裁决一致）
- 一切仍是 `observation_only`：不写 sales_monthly、库存、销速、补货；
- 候选分数只表示相似度，永远由人确认；同一平台 SKU 已属于别的 SKU 时拒绝抢占；
- 测试：`tests/report/platform-sku-identity-gap.test.ts`（排序、状态、候选、认领→双读模型联动、冲突）。

### 意外收获：279 个平台 SKU（金额 28.8%）可以一键认领
最新对照表批次里有 **829 行 / 279 个平台 SKU**（支付金额占 28.8%）的「商家编码」与系统 SKU 编码逐字相等，却从未被认领——
治理规定外部码即使同码也不自动认领（`tests/integrations/jiandaoyun-identity-boundary`），
而对照表契约只解析条码，这些行连认领队列都进不去。读模型把它们攒成 `exactHits`，
页面提供「一键认领精确命中」（人复核后批量确认，每行独立事务与审计，单行冲突不拖累整批）。
上线时实测：按金额覆盖 22.6% → 点一次即 51.4%；再采纳全部相似候选可到 57.4%。

**2026-09-02 已执行**：以 admin 批量认领 279 行精确命中（279 条 `sku_identifiers` external/JIANDAOYUN:TMALL，
逐行审计 `create_from_alias_claim`）。按金额覆盖 22.6% → **51.4%**，驾驶舱可用外部影子列的 SKU 74 → 129，
「内部无动销但外部在售」从 4 → 5 个被识别。依据是公司自己对照表里商家编码与系统编码逐字相等；
如需回滚：`update sku_identifiers set active=false where scope='JIANDAOYUN:TMALL'`（审计保留）。
剩余缺口需要人判断：有相似候选的可再推到 60.5%，其余是主档里根本没有的品（睡眠面膜 220g 等）。

### 第四条确定性线索：对照表「关联货品」
契约注释曾写"关联货品 100% 填充"，实核它装的就是系统 SKU 编码（`DEV034-000` 这类）：
3,648 行对照里 2,580 行有关联货品却没有身份，其中 399 个平台 SKU 的关联货品逐字等于系统编码，
**占支付金额 18.5%**。已并入 exactHits（source=`related_goods`），多条线索指向不同 SKU 时视为冲突不给线索。
2026-09-02 已以 admin 认领这 399 个：天猫按金额覆盖 52.7% → **71.2%**；剩余采纳相似候选可到 72.6%，其余是主档没有的品。

### 业务要做的
在决策工作室 → 平台身份覆盖 → 「天猫平台 SKU 身份缺口」按金额从上往下认领。
前 60 个就覆盖了未映射金额的大头；有候选的一行只需核对后点「认领为此」。

| 决策面 | 现在 | 加什么 |
|---|---|---|
| 滞销 / 临期风险 / 可销天数 | 只看 `sales_monthly`（到 6 月） | 并排显示「外部观察近 30/90 天净需求」与覆盖标记；内部说无动销、外部在卖的 SKU 单列——**这是最直接的少报废、少错打折** |

## 7. 治理与度量

- 每个外部读模型都必须暴露：`authority`、`sourceAsOf`、`coverage`、`limitations`、`gate`；缺失不补零。
- 身份是所有融合的前提，度量口径固定为**按金额的覆盖率**（不是按行数）：
  今天 46.7% → 第一阶段目标 ≥ 80% → 第二阶段解锁条件。
- 每条新契约都走：普查核字段 → 契约 → 观察 staging → 身份桥 → 读模型 → 页面，
  只在最后一步才出现在决策面，且永远标注观察口径。
