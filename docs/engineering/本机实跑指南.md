## 日常操作

```bash
# 启动
docker compose -f docker-compose.prod.yml -f docker-compose.local.yml --env-file .env.prod up -d

# 停止（数据保留在 docker volume 里）
docker compose -f docker-compose.prod.yml -f docker-compose.local.yml --env-file .env.prod down

# 看日志
docker compose -f docker-compose.prod.yml -f docker-compose.local.yml --env-file .env.prod logs -f app

# 改了代码后重新部署
docker compose -f docker-compose.prod.yml -f docker-compose.local.yml --env-file .env.prod up -d --build app

# 健康检查
curl -s http://localhost:3100/api/health
```

关机重启后 Docker 会自动拉起（`restart: unless-stopped`），只要 Docker Desktop 是开机自启的。

## 局域网访问（已开启）

**已配置完成**：同一网络下的同事可以直接打开

```
http://192.168.3.154:3100
```

（`docker-compose.local.yml` 绑 `0.0.0.0:3100`，`.env.prod` 的 `AUTH_URL` 已设为同一地址——
这两处必须一致，否则登录后回跳会指向 localhost 而失败。）

**本机 IP 变了怎么办**：笔记本换网络后 `192.168.3.154` 会变。
用 `ipconfig getifaddr en0` 查新地址，同步改 `.env.prod` 的 `AUTH_URL` 再 `up -d`。

**要收回成只有本机可用**：把端口改回 `"127.0.0.1:3100:3000"`，重启即可。

⚠ **开放前请想清楚**：这是明文 HTTP，同网段任何人都能访问，也能抓包看到登录信息。
内部小范围试用可以接受；长期使用应放到有 HTTPS 的服务器上。
另外笔记本合盖/断网时服务就没了——这也是它只适合试用、不适合当正式生产的原因。

## 真实数据已迁入（2026-08-04）

实跑库最初只有 `db:seed` 的演示夹具（4 个 SKU），**看起来像空系统**——
因为全部真实数据一直在开发用的 PGlite 文件库 `.data/dev` 里，
那是与 PostgreSQL 完全无关的另一个库。已用
`scripts/migrate-pglite-to-postgres.ts` 整体搬迁，逐表核对行数一致：

```
skus 5,376 · spus 348 · boms 818 / bom_lines 5,161
suppliers 156 · warehouses 25 · batch_stocks 1,767
sales_monthly 7,054 · transit_refs 9,182 · staging_rows 41,936 · users 13
共 64 张表有数据，89 个序列已重置
```

**迁移中踩到并已处理的三件事**（重跑时会遇到同样的）：

1. **只搬两边都有的表**：PGlite 的迁移账本叫 `_migrations`，PostgreSQL 叫
   `drizzle.__drizzle_migrations`，直接照源库清单操作会炸；账本本就不该搬。
2. **json/jsonb 列必须显式 `JSON.stringify`**：node-postgres 遇到 JS 数组会按
   **PostgreSQL 数组字面量**序列化而非 JSON，插进 json 列报
   `invalid input syntax for type json`。对象碰巧能过、数组不行，所以只在含数组的列上炸。
3. **必须重置序列**：显式插 ID 不会推进 sequence，不重置的话下一条新单据直接撞主键冲突——
   这类迁移最常见的事后翻车点。

> 开发库 `.data/dev` 保持原样未动（全程只读副本操作），可继续用于开发。
> 两边此后各自独立，不会自动同步。

## 账号

9 个角色账号已建好：admin / ops01 / purchasing01 / warehouse01 / warehouse02 /
quality01 / pmc01 / finance01 / pmc02。

**重新发一轮初始密码**（例如新同事加入、或密码发错了人）：

```bash
DATABASE_URL="postgres://scm:<密码>@127.0.0.1:15432/scm" \
  npx tsx scripts/set-initial-passwords.ts
```

该脚本给**每个账号各自独立**的随机密码，并置 `mustChangePassword=true` 首登强制改。
密码只打印到终端，**不写任何文件**。

> 为什么不共用一个密码：共用等于没有账号隔离——一个人泄露全员沦陷，
> 出了问题也分不清是谁操作的。审批与职责分离（审批人≠制单人）是这套系统的核心控制，
> 共用密码会直接把它架空。所以请**分别发给对应的人**，不要群发同一份清单。

## 排查时用得上的两个坑（都已修，记下来免得再踩）

1. **容器健康检查一直失败、但宿主机访问正常**
   Next.js standalone 默认绑到容器主机名对应的 IP，不是 `0.0.0.0`；
   healthcheck 用 `127.0.0.1:3000` 因此永远连不上。
   已在 compose 里设 `HOSTNAME: "0.0.0.0"`，并写进 `npm run check:ops` 防回归。
2. **数据库密码认证失败**
   PostgreSQL 的 `POSTGRES_PASSWORD` **只在首次初始化数据卷时生效**。
   卷已存在时改环境变量没用，要么进容器 `ALTER USER scm WITH PASSWORD '…'`，
   要么删卷重来（会丢数据，慎用）。
