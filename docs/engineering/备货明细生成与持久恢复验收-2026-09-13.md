## 修复与业务边界

| 缺口 | 已实现 |
|---|---|
| 任意一张WO使整张多行BH从建议消失 | 按原始`bhLineId`逐行显示待生成、已生成或需核对结果；部分成功不吞掉其余需求 |
| 同SKU多行按首项生成、界面行键冲突 | 请求、行键、忙碌状态使用准确来源明细ID；同SKU甚至同数量/日期的不同原行仍各自保留 |
| 重复请求或两人竞争可能重复建单 | 当前身份与BH锁内，工单、取号、审计、唯一明细回执同事务提交；同来源重放返回原WO，不新建 |
| 刷新后丢失生成结果 | 预演读取持久回执，显示“打开已生成工单”；返回当前真实状态，不将已流转单据误称未提交草稿 |
| 期望到货日期未传递 | 原行数量字符串和期望日期传到WO数量/交期，费用保持既有2位契约 |
| 钩子中间一行失败影响后续处理 | 各行独立原子生成，失败行ID留审计，其余合格行继续；之后仅补未生成行 |
| 旧WO无法可靠分配到BH某一行 | 同BH同SKU存在未分配WO时阻断新自动生成并回链原单，不自动猜测认领或回填历史 |

本次沿用审批钩子原本逐明细产草稿的方向，明确为**一条原始BH明细最多一张自动生成WO**，不是“一BH只能一WO”，也不是按SKU/数量去重。手工WO拆单政策不变；不宣称所有人工重复已禁止。原WO作废/关闭不删除凭据或自动再生，后续纠错须人工按业务依据处理。

写端先在事务内回查当前账号/角色/会话/范围，再锁来源BH、定位准确明细和读取回执。来源关闭后可恢复已有结果，但不得生成其余行；撤权后连重放也拒绝。旧BH/SKU请求只在唯一匹配明细时兼容，同SKU多行返回409，不能静默取首行。范围外仍404，读取与生成成功响应仍`private, no-store`。

新增`0067_bh_line_generation.sql`，总迁移68：`bh_wo_generations`保存明细ID、来源版本、WO、创建人及时间，来源明细和WO各自唯一，外键及UPDATE/DELETE/TRUNCATE拒绝触发器保护。**纯新增，不更新历史工单或回填关联。** 行锁设计参考[PostgreSQL官方锁文档](https://www.postgresql.org/docs/17/explicit-locking.html)，本项目实际等待与提交结果另由下述真实多连接测试验证。
