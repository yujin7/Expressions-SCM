## 目标与边界

让计划员从首屏看懂“需要复核的是什么”，点击后看到同一权限范围中的同一批事项。
本次修改展示和读取口径，不关闭/知悉真实告警、不改库存、派工、通知受众或D69–D71。
正式事实、最新分析和历史未处理队列保持分开；pending不是最新命中的同义词。

## 已确认反例

1. 旧`computeExceptionsUncached`只数`system_alerts.status=open`，却描述“连续3天爆单”“SKU仍断货”等当前事实。
   上游在缺证据时会有意保留旧项；同一SKU还可能有多条告警，不能当成去重SKU数量。
2. 爆单/断货卡链接最新分析，不一定能找到计数中的历史记录；时效/新鲜度未预选类别。
3. 受限用户看到全局爆单4条，而告警列表只允许1条；全局memo也不能复用于其他范围/展示策略。
4. 浏览器390px下，严重度加右侧操作把说明压成窄条；标题被访问时间挤掉。空清单的绿色“各项监控均在阈值内”
   与已打盹/证据不足矛盾；打盹使用无href的anchor，缺少原生键盘行为。

## 实现

- `focus.ts`通过既有`resolveChannelScope`、`visibleChannelScopedAlertIds`、`channelScopedAlertCondition`
  在SQL聚合前裁剪，复用`/api/alerts`同一规则；内部Map不进入DTO。
- 四类卡片保留key/severity，改“条未关闭告警”、待核对/复核及最新证据提示；统一
  `/alerts?category=…&status=open`。工作台系统告警入口总数也使用同一裁剪。
- 仅默认全局展示使用既有memo；带用户或定制recordShown/applySnooze策略不共享该memo。
- 无用户的后台调用标“全局”和“列表按查看者权限展示”；测试验证同一内容指纹重复运行0次新增入队。
  文案指纹变更可能在未来授权发布后按既有策略产生一轮更正通知，不重写历史、不承诺完全不发新通知。
- CSS module只作用于控制塔列表，640px以下动作在说明后，不缩小文字；标题/标记允许换行。
  32px操作高度，具名链接/按钮，原打盹弹窗继续显式说明全局影响。空态改信息提示。
