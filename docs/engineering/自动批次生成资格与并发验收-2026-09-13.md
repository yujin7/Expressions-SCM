## 为什么先修生成入口

采购 SH 入库的钩子会调用 `hookAfterPoReceipt`，后者再调用 `createBatchJg`。原生成方法在事务外预演全部工单/备货建议，然后直接按旧建议写草稿；没有事务内新鲜身份、工单状态和供应商状态保护。为它直接加重试会扩大旧快照与并发风险。

| 断点 | 本轮改变 | 保留的边界 |
|---|---|---|
| 旧会话仍声称PMC | 事务内 `currentWriteActor` 读取并锁定当前账号，再检查PMC/admin | 不给仓管增加PMC权限，不开启自动参数 |
| 两次同时生成 | 同WO先取得行锁，再读取当前批次数/数量/待批状态 | UNIQUE(woId,batchSeq)仍为数据库最后防线；生成仍是草稿 |
| 工单关闭、供应商暂停、产品停用 | 在写入事务中核对并持有相关行锁；预演也显示停用/暂停原因 | 黑名单/暂停禁止新单，存量收尾规则不变 |
| 到料数量在预演后改变 | 等待相关PO收退写方，再读取提交后的receivedQty | 仍按现行系统PO已收口径，不用旧台账旁证驱动数量 |
| 一个物料分多行需求 | 先按物料汇总grossReq，再复用该物料已收到料 | 50个到料、全单100件需200个物料：建议25件，不再误报50件 |
| 一个操作扫描全公司建议 | 提取共用批次预演函数；写操作只读取目标WO，不计算其他BH的WO建议 | 全局预演仍可查看全部；未声称全局页面性能已优化完 |
| 旧批次序号有间隔 | 以现存最大批次序号+1续接 | 单据号仍使用doc_counters；不回收旧序号、不删除旧单 |
| 失败残留草稿 | 草稿、费率首段、取号、审计在同一事务 | 审计故障全部回滚；无过账、无库存写入 |

锁设计依据 PostgreSQL 行锁在事务结束前保护所读行、并发更新会等待的语义，实际多连接验证也确认等待发生；不是仅检查代码里存在 `for update`。[官方行锁说明](https://www.postgresql.org/docs/current/explicit-locking.html)

## 未完成的业务与架构边界

1. PO入库后的best-effort自动JG钩子仍可失败；仓管发起入库但生成要求PMC，不能通过伪造角色解决。后续补持久失败可见、PMC恢复与准确来源入口；自动开关继续默认关。
2. 规格11的到料叙述为“委外仓余额+FL−TL”，现行代码生成数量为“本WO系统PO已收量”；ATP又使用系统库存/在途。三者不相同。本轮只修相同口径内部重复需求与事务安全，**未消除来源/仓库归属、占用与实到厂资格差异**；须结合来源链取证，不能简单将余额与历史收发相加。
3. 纯R18函数仍有数值转换与中间除法舍入，极小单耗/整件边界需专项验证；本轮十进制化已下批累加不代表全部数量精度已证明。
4. `generateDocs`、自动BH→WO、审批后到料的其他写入口尚需共同核对；本轮WO锁不证明所有历史写方均已统一锁序。保留唯一约束与已有人工审批闸。
5. 真实角色、真实数据资格、品牌灰度、全链UAT、外部系统业务接口、正式备份发布及D69/D70/D71仍未全部完成。

工作流技能要求先明确角色与异常路径，写路径技能促使先修可重试入口的安全前提；发布和浏览器技能分别验证精确候选及实际体验。未新增技能副本、依赖或迁移。3461运行、浏览器与隔离PG已核对owner/PID/cwd后停止，库/冻结包/截图/日志保留；正式3100、正式口令与外部数据未改。
