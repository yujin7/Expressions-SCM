# 2026-07-30 精益重构与 SKU 编码闭环计划

状态：红队通过，进入执行
依据：2026-07-27 会议纪要、20 份业务源文件、现行数据库/代码、`docs/spec/CURRENT.md`、`docs/spec/18-0727-meeting-delivery-plan.md`

## 1. 结论先行

系统应继续演进现有模块化单体，不重写、不拆微服务、不复制第二套库存或指标口径。本轮最有价值的
动作是：

1. 把未来 SKU 编码从“人工自由输入”升级为可自动取号、可校验、可解释的前向标准；
2. 保留全部历史商家编码和外部编码，通过稳定主码与别名继续解析，绝不批量换码；
3. 把 7 月 27 日会议要求按“已完成、需真实数据、需外部机器凭证、需试点”分层，不重复建设；
4. 清理构建缓存和重复发布产物，收紧 standalone 打包边界，但不碰业务数据库、备份、上传或迁移历史；
5. 压缩当前文档入口中的过期状态，让“现在做什么”与历史审计分开。

## 2. 实证基线

### 2.1 交付反馈

| 指标 | 当前实测 |
|---|---:|
| `npm run check:fast` | 6.80 秒，1,031 个测试 |
| 全量测试 | 48.58 秒，1,721 个测试 |
| GitHub 全量测试检查 | 9 分 32 秒 |
| 跟踪文件 | 1,096 个，约 16 MB |
| 工作区总量 | 约 3.6 GB |

工作区体积主要来自可再生输出：`.next` 约 1.2 GB、`.next-live` 约 1.0 GB、
`.next-dev` 约 301 MB、`.artifacts` 约 279 MB、`node_modules` 约 723 MB。
`.data`、`backups`、`uploads` 分别承载数据库、可恢复备份和业务附件，必须保留。

### 2.2 SKU 实证

抽取 10 份业务工作簿，共发现 5,023 次编码出现、857 个唯一编码。主要模式包括：

- `E054-000`、`N006-003`；
- `N02-003-a/b/c` 等版本后缀；
- `DEV025-000`；
- `E001-X000`、`E009-1-000` 等历史变体；
- `DEV025-0201-1`、`DEV025-0401`、`DEV025-ZY001` 等物料码。

现有码同时混入品牌、产品族、物料类别、版本和人工习惯，且共享包材证明“把父产品写进物料码”
会造成一物多码。故旧码只保留，不再把其结构继续复制到未来规则。

## 4. SKU 编码标准 S1

### 4.1 格式

`S1-{来源}-{类型}-{六位全局流水}-{两位校验码}`

示例：

- `S1-EXP-F-000123-K7`
- `S1-NING-P-000124-2M`
- `S1-GEN-R-000125-8C`

字段含义：

| 字段 | 含义 | 规则 |
|---|---|---|
| `S1` | 编码方案版本 | 固定；未来改规则必须升版本，不能重释旧码 |
| 来源 | 品牌起源或 `GEN` | 品牌短码取主档；共享/中性物料用 `GEN`；一经生成不因品牌转移而改码 |
| 类型 | `F/H/R/P/V` | 成品/半成品/原料/包材/服务 |
| 六位流水 | 企业全局身份序号 | `doc_counters` 原子取号；允许跳号，禁止 `MAX+1` |
| 两位校验码 | 录入防错 | 对前四段计算；用于发现常见误录，不是安全签名 |

### 4.2 明确不编码的内容

渠道、供应商、工厂、规格、颜色、售价、生命周期、销售状态、当前 BOM 父项和法规市场均不进入
永久编码。这些字段会变化，且系统已有结构化字段或关系表；把它们重复写进编码会制造换码和重复
主档。

### 4.3 新旧边界

- 存量 `skus.code` 原样冻结。
- 外部系统码、旧码和条码继续通过 `aliases` 解析。
- staging/release 导入继续接受历史真实编码，不套用 S1。
- 主数据页面新建 SKU 时，编码留空即由服务端在同一事务内生成 S1。
- 若人工输入历史/外部码，继续按宽容规则建档；`S1-` 命名空间仅允许系统原子取号，
  防止不同来源或类型人工复用同一企业全局流水。
- 更新已有 SKU 时仍禁止改主码。

## 5. 红队审计

| 方案/风险 | 结论 |
|---|---|
| 批量把 5,376 个 SKU 换成新码 | 拒绝：会破坏单据、BOM、库存、附件和外部对照 |
| 延续 `E/N/DEV + 产品族 + 物料段` | 拒绝：现有文件已证明结构不一致且共享包材会一物多码 |
| 在码中加入渠道或版本文字 | 拒绝：渠道和展示版本可变，且已有结构化字段 |
| 按品牌分别计数 | 拒绝：品牌变更或并购时可能碰撞；全局流水更简单 |
| 预览时提前占号 | 拒绝：取消表单会制造无意义号码消耗；只在保存事务内取号 |
| 强制所有导入立即使用 S1 | 拒绝：会阻断真实历史数据和外部系统对账 |
| 只做正则、不做并发取号 | 拒绝：无法解决重复与人工录入问题 |
| 把校验码当安全控制 | 拒绝：它只防误录；权限、唯一约束和审计仍是权威 |
| 为 SKU 标准另建第二张主表 | 拒绝：现有 `skus`、`brands`、`aliases`、`doc_counters` 足够 |
| 删除 `.data`、备份、上传、迁移快照 | 拒绝：均属于恢复或业务证据 |
| 因大文件直接拆服务/微前端 | 拒绝：当前性能证据不支持架构扩张 |

红队后的收敛结论：S1 是前向自动取号能力，不是历史改码工程；编码只承载稳定身份的最小信息，
业务语义由主档字段、SPU、BOM 和别名承载。

## 6. 执行批次

### P0 - 本轮实现

1. 新增 S1 纯函数：生成、解析、校验码、类型映射、品牌来源归一化。
2. 新增事务内全局取号，碰撞时继续取号；禁止 `MAX+1`。
3. SKU 新建支持编码留空自动生成；S1 手输必须与品牌和类型一致。
4. SKU 页面增加清晰的编码标准说明和示例，保留历史/外部码入口。
5. 覆盖纯函数、并发/碰撞、创建、历史兼容、错误 S1、更新冻结测试。
6. 更新 D31、能力台账和当前入口，消除“规则仍待定”的过期状态。
7. 从默认 standalone 追踪中排除本地备份、上传和数据库目录，避免把恢复证据复制进构建产物。
8. 扩展安全缓存清理脚本，删除可再生构建/验证输出，但永不触及数据、备份、上传和依赖。

### P1 - 需要真实业务输入

1. 导入并人工确认 7 月末样品库存分类。
2. 指定两款产品和业务/供应链/财务试点用户，执行真实下单到结算 UAT。
3. 清理未归类用途、重复候选、品牌缺失和 301 个未认领物料编码。
4. 用真实物流周期、保质期、渠道和仓库覆盖校准补货与风险口径。

### P1 - 需要外部机器资料

1. 聚水潭：应用授权、商家范围、接口权限、IP 白名单和对账基准。
2. 飞书：自建应用凭证、权限、目标会话与测试群 UAT。
3. 用友：企业开放平台机器应用、租户/组织/账套、获批 API 和沙箱；个人网页登录凭证不进入系统。

## 7. 完成判据

- 所有旧 SKU 和别名解析行为不变；
- 并发新建不会重复编号；
- S1 可由人和系统稳定解释，错误校验码被拒绝；
- 自动编码的写入与审计同事务；
- `check:fast`、全量测试、构建、真实 PostgreSQL 迁移契约和浏览器关键流均通过；
- GitHub 通过受保护分支的 PR 合并，不绕过 required checks；
- 代码、文档、工作区和 Git 状态干净，无业务证据被误删。
