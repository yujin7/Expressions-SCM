# 让所有人访问系统 — 现行方案与运维手册

日期：2026-08-12
状态：**临时公网入口已开通；固定域名仍待接入域名**

## 现在怎么访问

链接由守护进程管理，随时可查：

```bash
npm run access:link
```

- 任何设备、任何网络都能打开，**同事什么都不用装**
- 真 HTTPS（Cloudflare 终止 TLS），密码不再明文传输
- 与本机局域网 IP 完全无关 —— 换 Wi-Fi、IP 再漂都不受影响
- 当前快速隧道不需要域名，0 费用；地址不是永久地址

### 2026-08-12 固定地址复核

- Cloudflare 账户已经登录，具名隧道 `7588fd39-a171-45d5-9667-6d077325c88a` 已建立并保持
  4 条连接；这只证明隧道进程在线。
- 该具名隧道目前**没有 ingress/public hostname**，访问请求会返回 503；不能替代现行快速隧道。
- Cloudflare 账户的 Domains 清单为空。Cloudflare Tunnel 不能凭空分配固定的
  `expscm.cloudflare.com` 或固定 `trycloudflare.com` 名称；必须先购买域名，或把已有域名的
  DNS zone 接入这个账户。
- 最小长期方案：接入一个域名后，把 `scm.<你的域名>` 绑定到上述具名隧道，服务指向
  `http://localhost:3100`；验证健康、登录回跳与权限后，再停用快速隧道。
- 在固定域名真正通过端到端验证之前，快速隧道和飞书自动换址通知必须保留，不能为了“看起来永久”
  先关掉唯一可用的公网入口。

## 为什么是这个方案

约束：不买域名、不注册任何服务。在这个约束下逐个实测的结果：

| 方案 | 结果 |
|---|---|
| `expscm.local`（mDNS） | ✗ `.local` 按定义只在同一网段内有效（RFC 6762，靠组播、不经路由），走不出这栋楼；Windows/安卓常常连同网段都解析不了 |
| Cloudflare **具名**隧道 | △ 隧道已在线；仍需自有域名和 public hostname 才能形成固定地址 |
| Tailscale | ✗ 需要注册登录，且每位同事都要装客户端 |
| serveo.net | ✗ 2026-08-07 实测 22 端口连接超时，项目已不可靠 |
| localhost.run | ✗ 实测 20 秒无响应，不可依赖 |
| **Cloudflare 快速隧道** | ✓ **0 注册、0 费用、真 HTTPS、同事零安装** |

### 快速隧道的唯一代价

**地址在 cloudflared 进程重启时会变**（由 Cloudflare 随机分配，无法指定）。

守护进程就是为了让这个代价不落到人身上：

1. **同时守 PID 与公网端到端健康**——进程活着但 DNS/控制流已死也会被识别；
2. 连续三次公网健康/登录回跳失败就终止旧隧道并申请新地址；
3. 地址变化后**自动**同步 `AUTH_URL` 并重启应用；
4. 公网健康与登录回跳都通过后才**把新链接推到飞书群**。2026-08-10 实测旧版只看 PID
   会漏掉死亡隧道，新 watchdog 已自动换址恢复。

### 传输协议：必须 HTTP/2（2026-09-02 实测）

cloudflared 默认 QUIC(UDP)，出境实测被显著劣化。同一时刻、同一应用、同一台机器：

| | QUIC（默认） | HTTP/2（现行） |
|---|---:|---:|
| `/api/health` 往返 | 0.65–1.4 s | 0.32–0.42 s |
| 并发拉取工作台 33 个前端分块（墙钟） | 4.3–7.8 s | 2.0–2.8 s |
| 本机直连同一接口 | 8–15 ms | 8–15 ms |

用户感受到的"慢"几乎全在出境这一跳（服务端所有页面 SSR < 30 ms、绝大多数接口 < 160 ms）。
守护脚本已固定 `--protocol http2`，护栏：`tests/architecture/public-tunnel-transport.test.ts`。

**试过并否决**：把 webpack 分块改粗（minSize 200 KB、请求数上限 8）确实让分块数减半
（中位数 26 → 13/页，工作台 33 → 18 个文件），但同一隧道上并发拉取全部分块的墙钟 2.3 s → 2.6–2.9 s，
没有变快——HTTP/2 多路复用下并发请求的开销本就很小，字节数不变就没有收益，
反而每次发布后要重新下载更大的块。已回退，别再盲试。
浏览器首次打开一个页面要拉 30 余个 JS 分块，分块带 `immutable` 缓存头，第二次起走本地缓存；之后每次导航≈1 次 HTML 往返 + 1–2 次接口往返。

### 2026-09-02 复盘：链接为什么一天换好几次

守护日志统计（8/22–9/2）：**每天换址 2–8 次**，其中 32 次是守护自己把刚建好的隧道判死重建
（新 quick tunnel 的 DNS 传播常超过 30 秒，而旧逻辑只等 30 秒）。17:44–17:49 一次升级就连换 4 个地址、
重启应用 4 次、飞书群收到 4 条链接。已修：

- 新地址等足 3 分钟再判失败；探针超时 2 s/3 s → 5 s/10 s（隧道往返本就 0.6–1.4 s）；
  连续失败阈值 3 → 5；本机应用未就绪时不计入隧道失败；
- **守护重启不再换址**：cloudflared 用 `setsid` 放进独立会话（launchd 在守护退出时会 SIGKILL 整个任务
  进程组，首次实测接管就是这样失败的），新守护启动时探活并接管旧隧道。升级守护脚本的做法：
  把新脚本复制到 `~/Library/Application Support/exp-scm/` 后 `kill -9` 守护进程，launchd 拉起新版本，
  实测地址与隧道进程均不变（`npm run access:public` 会重建隧道，只在改 compose/env 时用）；
- 修正安装/卸载脚本的 `pkill` 模式（加了 `--protocol http2` 后原模式匹配不到，会留下两条隧道）。

Cloudflare 自己重置账号级快速隧道导致的换址仍然存在，这是免费方案的固有代价。

### 为什么每次都要动 AUTH_URL

`AUTH_URL` 必须与同事**实际输入的地址**完全一致，否则登录后回跳会指向一个不存在的地方。

实测过一个坑：**留空不行** —— standalone 容器里 credentials 回调会解析成服务端自身
绑定地址 `http://0.0.0.0:3000`，即便 `trustHost: true` 也一样。所以一律显式写。

## 运维命令

```bash
npm run access:link            # 查当前链接并验活
npm run access:public          # 开通/重装（幂等）
npm run access:public:remove   # 关闭公网入口
tail -30 ~/Library/Logs/scm-public-tunnel.log   # 看守护日志
```

关闭公网入口后若还要在局域网用，跑 `npm run lan:sync` 把 `AUTH_URL` 切回局域网地址。

### 实现要点（改之前先读）

- **守护脚本跑在 `~/Library/Application Support/exp-scm/`，不在仓库里。**
  仓库在 `~/Downloads` 下属 macOS TCC 保护目录，**launchd 派生的进程读不到**
  （2026-08-07 实测 `READ_ENV=DENIED`）。安装脚本因此把 compose 与 env 复制出去；
  而 docker CLI 在同一环境下正常（只走 daemon socket，不碰受保护文件）。
- **compose 必须带 `-p supply-chain`。** 换目录跑 compose 会按新目录名另起项目，
  挂**全新空卷**——表现就是「数据全没了」。既有卷是 `supply-chain_pgdata` / `_uploads`。
- **AUTH_URL 用环境变量覆盖，不改 env 文件。** compose 插值优先级是
  shell 环境 > `--env-file`，因此磁盘上始终只有一份配置，不会出现两份真相。

## 上公网前做的安全审计（2026-08-07）

18 个 agent 分五个视角（中间件放行面、路由鉴权、实测可达面、响应头/Cookie、限速与种子口令）
交叉排查，每条疑似暴露再由独立 agent **实测证伪**。

### 结论：没有数据泄漏

未登录状态下全部业务页 302 跳登录、全部业务 API 401、全部写接口 401。
公开白名单只有三个根（`/supplier/confirm`、`/e-label`、`/api/public`），
均由 token 门控，伪造 token 一律 404。

### 已修复

| 问题 | 处置 |
|---|---|
| **限速键可伪造**：`clientIpOf` 取 `x-forwarded-for` **首跳**，而左侧各跳由客户端自带。实测固定 XFF 第 21 次起被限，**轮换 XFF 则 40/40 全部穿透** | 改为 `cf-connecting-ip` > XFF **最右**跳 > null。护栏：`tests/redteam/client-ip-trust.redteam.test.ts`（已验证回退旧实现即变红） |
| **HSTS 门控无效**：`PUBLIC_HTTPS` 接在 compose 运行期 `environment:`，但 `headers()` 由 `next build` 求值后烘焙进 routes-manifest，运行期设了不起作用。实测容器 env 有 `PUBLIC_HTTPS=1` 而响应头无 HSTS | 改为 Dockerfile build ARG + compose `build.args`。护栏：`tests/architecture/build-time-env.test.ts` |
| `/api/public/po-confirm/[token]` 缺 `Cache-Control` | 补 `private, no-store` + `nosniff`，与同目录 e-label 对齐 |

### 尚未处置，需要你拍板

**账号锁定可被用作拒绝服务。** 连续 5 次失败即锁账号 15 分钟，而种子用户名固定可预测
（`admin`/`ops01`/`purchasing01`/`warehouse01`/`warehouse02`/`quality01`/`pmc01`/`finance01`/`pmc02`），
且系统会用 `code=locked` 明确告诉攻击者锁定生效了。

修掉限速伪造后，单个来源已被压到 20 次/5 分钟，成本大幅上升；但**这不是根治**——
锁定策略本身允许任何知道用户名的人锁掉该账号。三个选项：

1. **改按（用户名+IP）锁定**，而不是全局锁用户名 —— 推荐，不影响正常用户体验；
2. 改成渐进延迟（每次失败等待翻倍）而不是硬锁；
3. 维持现状，接受这个风险（内部小团队、链接不公开传播时可接受）。

这是安全策略取舍，不该由我替你定。

**另外两条既有加固项**（本轮未动，非本次上公网引入）：
- 无 CSP（AntD 5 大量运行时内联样式，需 Report-Only 跑一轮再收敛，是独立任务）
- 种子账号共享同一初始口令且未强制改密 —— 建议尽快让每人改掉

## 长期：这套东西终究要挪出笔记本

隧道解决的是**地址**，解决不了**「这台机器是笔记本」**：
合盖、休眠、带电脑出门、切 VPN —— 每一样都会让全组断线，跟地址无关。
Cloudflare 也明确说明账号级快速隧道**不保证可用性**、不适合生产长期使用。

只要这套系统成为团队日常依赖，最终都得挪到一台常开的机器上：

- 一台 2 核 4G 云主机（阿里云/腾讯云轻量）约 ¥60–100/月
- 固定公网 IP + 域名 + TLS，7×24 在线
- 现有 `docker-compose.prod.yml` 可直接用，迁移主要是搬数据卷
- 需要迁：PostgreSQL 数据、`uploads/` 附件、`.env.prod` 密钥（**密钥须重新生成**）

在那之前，现在这套是免费约束下能做到的最好结果。
