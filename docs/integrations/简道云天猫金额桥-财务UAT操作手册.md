# 简道云天猫金额桥：财务 UAT 操作手册

适用范围：简道云天猫支付金额、成功退款金额、平台费用支付金额三条只读观察流。
目标：由财务在同一业务范围、同一完整自然月和同一店铺下，证明 SCM 控制数与源系统一致，
并明确所有非零差异、缺失来源和冲销的处理结论。

> 本手册不授权财务入账。验收通过前，数据固定为 `observation_only`；即使验收通过，
> 在折让、拒付、商品成本、币种和用友关账尚未闭合前，也不得称为毛利或会计利润，
> 不得生成凭证、自动定价或自动改变供应计划。本文不记录账号、密码、API Key 或 token。

## 2. 角色与职责

| 角色 | 必须完成 |
|---|---|
| 财务 owner | 确认币种、费用分类、冲销口径、源平台控制总量和差异结论 |
| 电商数据 owner | 按相同店铺、日期、状态和时区导出支付与成功退款源表 |
| 平台账单 owner | 导出费用明细，保留费用项、原币、原正负号和账单调整 |
| 系统管理员 | 运行受控同步、保存批次证据、计算文件 hash、验证失败重跑与权限边界 |
| 财务负责人 | 对最终核对包签认，决定是否维持观察或进入下一授权层级 |

在 SCM 打开：`财务结算 → 毛利视角`。

## 3. 下载两份系统证据

1. 在“天猫渠道金额贡献桥（完整月观察）”点击“导出金额桥 UAT 核对包”。
2. 在“天猫平台费用结构（财务 UAT 预览）”点击“导出平台费用 UAT 控制总量”。
3. 金额桥核对包必须同时包含：
   - 三条 `source_control`：来源流、批次源更新时间、业务日期、源行、staging 行、有效/无效行；
   - `month_control`：每个完整月的支付、退款、净回款、平台费用和产品成本前贡献；
   - `latest_closed_month_shop`：最近完整月逐店铺数据，含缺失来源与被排除费用；
   - 人工填写栏：源系统核对值、差异金额、差异原因、责任人、期限、证据编号、签认状态。
4. 两份文件的权限口径必须为 `observation_only`，最近完整月和业务截止不得为空。
5. 对两份 SCM 文件及三份源系统导出分别计算 SHA-256，保存到受控证据目录；不要覆盖旧文件。

若导出按钮不可用，或页面显示 `insufficient`，立即停止。缺少任一最新成功批次时不得继续核对，
更不得把缺失值当作 0。

## 4. 冻结同一核对范围

三份源导出必须使用完全一致的：

- 完整自然月与时区；首轮使用 2026-07，后续滚动使用最新完整月；
- 天猫店铺范围；店铺改名须提供旧名到新名的受控映射；
- 支付状态和成功退款状态；取消、未付款、退款申请中不能混入；
- 币种和金额精度；禁止跨币种直接相加；
- 迟到更新截止点；源导出时间不得早于 SCM 批次源更新时间。

任一范围无法证明时，不做“近似一致”判断，直接记为待处理。

## 5. 四层核对顺序

### A. 来源批次控制

逐条核对 `source_control`：源行数必须等于 staging 行数；无效行必须为 0，或每一行都有明确
原因与处理结论。来源业务日期必须覆盖被验收的完整月。

### B. 月份控制总量

按同一月份和币种核对：

| 指标 | SCM 公式 | 验收方式 |
|---|---|---|
| 支付金额 | 简道云支付金额合计 | 与支付源导出逐分一致 |
| 成功退款金额 | 成功退款金额合计 | 与退款源导出逐分一致 |
| 净回款观察 | 支付金额 − 成功退款金额 | 独立重算一致 |
| 平台费用 | 费用支付金额原符号合计 | 与费用源导出逐分一致 |
| 产品成本前渠道贡献 | 净回款观察 − 平台费用 | 独立重算一致 |

工程侧不擅自设置金额容差。相同数据范围理论上应逐分一致；任何非零差异都必须解释和签认。

### C. 店铺核对

逐店铺重复 B 层核对。只有支付、退款、费用三源在同一店铺月份都有记录时才标记可比。
费用孤岛、销售孤岛或退款孤岛必须留在表中，`缺失来源` 不得清空，也不得通过人工填 0 消除。

### D. 费用结构与冲销

用第二份平台费用控制表按币种、月份、店铺、费用项下钻。逐项确认：

- 负数冲销保留负号，且能追到源账单调整；
- 计费金额与支付金额差异有业务解释；
- 进口关税、基础服务、干线、仓储等费用分类符合财务用途；
- 没有 SKU 直接归属证据的费用不按销量、金额或件数自动分摊。

## 6. 差异处理

在金额桥 CSV 的人工栏逐行填写：

| 差异原因分类 | 处理方式 |
|---|---|
| 范围/店铺不一致 | 重新冻结范围并重新导出，不手工调平 |
| 时区/自然月边界 | 统一时区和完整月后重跑 |
| 迟到更新 | 记录源更新时间，生成新批次；旧批次不改写 |
| 状态口径 | 由财务和电商 owner 确认支付/成功退款定义 |
| 币种/汇兑 | 分币种核对；未批准汇率前不折算 |
| 冲销/账单调整 | 保留原符号并关联源单据或账单说明 |
| 店铺身份缺失 | 建立带 `JIANDAOYUN + shop` scope 的映射后重跑 |
| 未知 | 保持阻塞，指定 owner 和期限，不以 0 或“其他”关闭 |

## 7. 必须停止的情况

出现任一项即停止签认：

- 三条来源不是各自最新成功、不可变批次；
- 核对月不是完整自然月，或三源业务日期没有共同覆盖；
- 源行数与 staging 行数不一致且无拒收证据；
- 无效行、币种冲突或店铺为空未处置；
- 同一店铺月份缺任一来源，却仍计算金额桥；
- 负数冲销被转正、删除或净额掩盖；
- 平台费用被称为收入减少、商品成本或毛利；
- 差异只能靠删行、改旧批次、手工改数或补 0 消除；
- 文件 hash、批次、owner 或签认记录缺失。

## 8. 完成证据与签认

一次 UAT 只有同时具备以下内容才可完成：

- 金额桥 UAT 核对包、平台费用控制表和三份同范围源导出；
- 所有文件 SHA-256 或受控文档版本；
- 所有非零差异的原因、owner、期限和最终结论；
- 费用孤岛和缺来源店铺的处置结果；
- 一次相同来源重跑不重复的证据，以及一次失败不推进 checkpoint 的证据；
- 财务 owner、电商数据 owner、平台账单 owner、系统管理员和财务负责人签认；
- 非秘密证据编号，例如 `UAT-202607-JDY-TMALL-FIN-001`。

签认结论只能选择：

1. `不通过`：继续保持观察，修复后生成新批次重验；
2. `条件通过`：记录残余缺口、期限和禁止用途，仍不进入会计权威；
3. `金额观察通过`：允许作为经营解释输入，但必须等用友关账、折让/拒付、成本和币种闭环后，
   才能另行申请正式净收入或贡献毛利权限。
