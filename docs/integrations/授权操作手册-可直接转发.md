# 供应链系统｜三方授权操作手册

> **给谁看**：负责用友、聚水潭、飞书后台的同事；第四节给负责货品档案的同事。
> **要做什么**：前三件各约 1–5 分钟，做完供应链系统就能自动取数、自动发告警；
> 第四件（补条码）是持续工作，决定电商日销量能不能自动对到货品上。
> **不需要**：不需要懂代码，不需要读其它文档，不需要提供任何密码给别人。
> **本文不含任何密钥**，可直接转发。

## 为什么需要你

供应链系统的对接程序已经写好并测试通过，鉴权也已经打通——
但**三个平台都要求由账号持有人本人在后台点一次授权**，程序无法代劳。

## 一、用友 —— 勾选 8 条只读接口（约 5 分钟）

### 现在的状态

系统已经能连上用友网关并成功取到令牌（说明 AppKey/密钥都对），
但调用任何业务接口都返回：

```
310037  API未被授权：APPKEY[5559d925…]未获得要调用的API[…]的授权
```

翻译：**用友认得这个应用，只是还没把具体接口勾给它**。

### 你要做的（**路径很隐蔽，请照下面走**）

⚠ 不在「开放平台/开发者中心」里，而是在 **YonSuite 业务系统内**：

1. 用**管理员账号**登录 https://c4.yonyoucloud.com/
2. 打开 **【API调用】** 这个节点（不是开发者中心，是 YonSuite 里的功能节点；
   找不到就用顶部搜索框搜「API调用」）
3. 点 **「添加应用」**，把我们的应用加进去（AppKey 以 `5559d925` 开头）
4. **鼠标悬停在刚加的那一行上** —— 行的右侧才会浮现 **「API授权」** 按钮，点它
   （这个按钮不悬停就看不见，很多人卡在这一步以为没有授权入口）
5. 在授权列表里勾选下面 8 条接口：

| # | 接口名 | 接口路径（可用于搜索） |
|---|---|---|
| 1 | 分页查询当前租户组织架构 | `/yonbip/uspace/org/page_list` |
| 2 | 供应商档案列表查询 | `/yonbip/digitalModel/vendor/list` |
| 3 | 物料档案分页查询 V2 | `/yonbip/digitalModel/product/listproductbycondition` |
| 4 | 采购订单列表查询 | `/yonbip/scm/purchaseorder/list` |
| 5 | 采购入库列表查询 | `/yonbip/scm/purinrecord/list` |
| 6 | 现存量查询 V2 | `/yonbip/scm/stock/QueryCurrentStocksByCondition` |
| 7 | 存货成本查询 | `/yonbip/EFI/fieia/queryBalance` |
| 8 | 凭证列表查询 | `/yonbip/fi/ficloud/openapi/voucher/queryVouchers` |

6. 保存后告诉技术侧一声

### 需要担心安全吗

**8 条全是查询类接口，系统不会往用友写入或修改任何数据。**
用友里的凭证、成本、采购单都不会被这个程序改动，它只读来做对账。

### 做完怎么验证

技术侧运行一条命令即可看到 8 条逐条变绿：

```bash
npm run yy:probe
```

组织架构那条一通，系统就能自己读出租户 ID 和组织 ID，**不需要你手抄任何编号**。

## 二、聚水潭 —— 申请 4 个接口权限（约 5 分钟，审批通常 5 分钟内）

### 现在的状态

**授权已经完成了**（2026-08-04），token 有效期 360 天，系统已能通过验签。
实测调用接口返回：

```
190  验证失败！无API权限，请申请API权限
```

翻译：**身份没问题了，只是还没给这个应用开放具体接口**。

### 你要做的

1. 登录聚水潭开放平台 → 右上角 **控制台** → **应用详情**
2. 打开 **「API权限申请」** 页面
3. 申请下面 **4 个接口**（系统只用这 4 个，都是查询类，不写入聚水潭）：

| 接口路径 | 用途 |
|---|---|
| `/open/shops/query` | 店铺查询——把平台店铺对上系统渠道 |
| `/open/wms/partner/query` | 仓库查询——把聚水潭仓库对上系统仓库 |
| `/open/orders/out/simple/query` | **出库单查询——每日实际销量的来源** |
| `/open/inventory/query` | 库存查询——与系统账做对照 |

4. 提交后等审批（官方说明一般 5 分钟以内），通过后告诉技术侧

### 需要担心安全吗

**4 个全是查询接口，系统不会往聚水潭写入或修改任何数据。**

### 做完怎么验证

技术侧跑一次真实拉数即可看到店铺、仓库、出库单的实际条数。

## 三、飞书 —— 给群加一个自定义机器人（约 1 分钟）

### 现在的状态

告警消息**已经能成功发出**（实测已投递到测试群）。
但目前用的是「总经办数据应用」，那是一个公司级大权限应用。

### 为什么建议换

供应链系统只需要一个能力：**往一个群里发消息**。
而「总经办数据应用」持有 **1107 项权限**，覆盖公司飞书的文档、通讯录、日历、审批等几乎全部数据。
把它常驻在供应链服务器上，等于让一台业务服务器握着能打开全公司飞书的钥匙——
一旦那台机器出问题，泄露的是整个飞书而不是一个告警群。

系统内置的安全检查因此**拒绝**把当前配置标为「可投产」。这个拦截是对的，我们没有绕过它。

### 你要做的（推荐路线，最省事也最安全，约 1 分钟）

1. 进入要接收告警的群 → 右上角 **「更多」** → **「设置」**
2. 右侧设置面板 → **「群机器人」** → **「添加机器人」** → **「自定义机器人」**
3. 名称填「供应链系统告警」，可加描述与头像 → 点 **「添加」**
4. **安全设置建议勾选「签名校验」**（系统已支持），把它给出的**密钥**一并发给技术侧；
   不勾也能用，但那样任何拿到 webhook 地址的人都能往群里发消息
5. 复制生成的 **Webhook 地址**（形如
   `https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxx`），连同上面的密钥发给技术侧

> 飞书官方提示：webhook 地址要妥善保管，不要贴到可公开查阅的地方。
> 这也是建议开签名校验的原因——万一地址流出，没有密钥仍发不了。

**自定义机器人只能往这一个群发消息，对公司飞书没有任何读取权限**，
不用发布、不用审核、不用等管理员批。

### 另一个选择

如果希望走应用机器人（能力更多），就新建一个自建应用，
**只申请这 3 项权限**：`im:message:send_as_bot`、`im:chat:readonly`、`application:application:self_manage`，
发布后把机器人拉进群，再把新的 App ID / App Secret 给技术侧。

### 还有一件小事

系统已建了一个群「供应链系统告警」，但目前**只有机器人一个成员**。
请把赵总和相关责任人拉进去，否则告警发出来没人看得到。
（也可以不用这个群，直接指定你们已有的群，把 webhook 给技术侧即可。）

## 数据什么时候更新

系统**每天同步两次**，都赶在你需要看数之前：

| 时间 | 发生什么 |
|---|---|
| **10:00–10:45** | 依次从用友、聚水潭、简道云取数 |
| **11:00–11:40** | 对账、检查数据是否过期、把异常推到飞书群 |
| **16:00–16:45** | 傍晚再取一次 |
| **17:00–17:40** | 对账与告警，下班前推送 |

所以你在**午饭前**和**下班前**看到的都是当天的新数据。
不是实时的——如果刚在用友里改了单据，要等下一个同步点才会反映过来。

（原本是每 6 小时一次，半夜那两次没人看，还白占三方接口的调用额度，已经取消。）

## 四、简道云（不需要后台授权，但需要补条码）

简道云这条线**已经在跑**：系统能读到 9 个应用、297 张表单，
其中天猫日销量 5 万行、SKU 对照 3 千行都已进入受控暂存区，数据更新到昨天。

**问题在于：平台商品要靠「条码」才能对上我们系统里的货品。**

实测结果：

- 平台上的「商家编码」和我们系统的货品编码**不是一套**（对上 0 个），指望不上；
- 靠条码能对上，但目前只对上 **72 个货品**（我们系统里共 5,376 个）；
- 我们也试过用程序做各种条码格式转换来多对上一些，**一个都没多对上**——
  说明对不上的条码是我们系统里**根本没录**，不是格式问题，程序解决不了。

### 需要业务做的（不用补几千个，前十几个就够回收大半）

听起来像大工程，实际高度集中。技术侧跑一条命令就能给出**按销售额排序**的待补清单：

```
缺条码的商品 597 个，涉及成交额 ¥1,066 万
  第 1 名  ¥68.6 万  NING补水睡眠面膜 220g
  第 2 名  ¥55.0 万  NING补水睡眠面膜 110g
  第 3 名  ¥54.8 万  NING氨基酸洗面奶 200ml
  …
  补完前 12 个 → 覆盖缺口金额的 39%
```

集中在 NING 旗舰店的几个主力单品（睡眠面膜、洗面奶、清洁泥膜的不同规格）。

1. **在天猫后台给清单上的商品补条形码**——从金额最大的开始补；
2. **确认我们系统的货品档案里同款也有同一条码**——两边都有才对得上。

补完前 12 个，电商销量的可归属比例大约从 **24% 提到 47%**
（这 12 个占缺口金额的四成，但只占总成交额的两成多——两个比例不要混）。
而且这是上限：**必须两边都补**——天猫后台填了条形码，我们主档里同款也要有同一条码，
只补一边对不上，等于没补。
需要清单请找技术侧要（命令：`npm run jdy:barcode-gap 40`）。

### 为什么这件事值得做

补齐之后，天猫/唯品会的**每日实际销量**就能自动对到每个货品上，
不用再人工导销量表；补货、可销天数、滞销判断都会基于真实日销数据。

**在补齐之前，系统不会拿这些数据算销速**——因为覆盖不全的销量会让
没对上的货品显示成「零销量」，被误判为滞销。宁可不用，也不能用错。
