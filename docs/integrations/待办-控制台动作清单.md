## 0. 顺带修掉的一个隐患：`.env` 与 `.env.local` 双配置源

原先仓库里同时存在 `.env` 和 `.env.local`，且**有 7 个键取值不同**。
Next.js 的加载顺序是 `.env.local` 覆盖 `.env`，于是出现了两套事实：

- 我的探针脚本读 `.env`，应用读 `.env.local`，两边 `YY_BASE_URL` 指向**不同集群**；
- 讽刺的是 `.env.local` 里那个值（`c4.yonyoucloud.com/iuap-api-gateway`）**才是对的**，
  我一度把它"修正"成 `api.diwork.com` —— 见下节第 2 条，那次修正本身是个错误。

同一个问题还让体检误报："简道云缺 API Key"——其实 key 一直配在 `.env.local` 里，
只是体检脚本没读那个文件。

已处理：把 `.env.local` 的键并入 `.env`（冲突项保留实测校正值），删除 `.env.local`，
**现在只有 `.env` 一个配置源**；体检脚本固化为 `npm run readiness`，与应用读同一份。
原文件已备份到本次会话的 scratchpad。

## 1. 飞书 —— 通道已打通，但**当前应用权限过大，不建议投产**

### 已经证明能用的部分

- `tenant_access_token` 获取成功；
- 用机器人**新建了一个群「供应链系统告警」**（`chat_id` 已写入 `.env`）；
- **向该群真实发送了一条测试消息，返回 `code=0 msg=success`**。

也就是说：飞书通知链路是通的，不是"写了没验证"。

### 但是：内置只读探针报出了一个安全问题

「总经办数据应用」声明了 **1107 项权限，其中 1007 项为高敏权限，1104 项在通知场景所需范围之外**。
系统判定 `extreme_over_privilege`，并拒绝把该连接器标为"可投产"：

```
evidenceReadiness: blocked_extreme_over_privilege
→ 权限数量远超 SCM 通知最小集合；停止生产接入，改用专用最小权限应用
```

**为什么这条不能绕过：** 供应链系统只需要"往一个群发消息"。若它持有这把钥匙，
等于让供应链系统同时能读公司飞书里的文档、通讯录、日历、审批、人事等几乎全部数据。
一旦这台服务器或这份 `.env` 出事，暴露面是整个公司飞书，而不是一个通知群。
我没有替你把这条护栏关掉——它拦得对。

### 你需要做的：两条路，**推荐第一条**

#### 路线 A（推荐，约 1 分钟，且权限风险为零）：群自定义机器人 webhook

供应链系统只需要"往一个群发消息"。**群自定义机器人**正好只能干这一件事——
它对公司飞书的文档、通讯录、日历、审批**没有任何读取权限**，
比"再建一个最小权限应用"还要安全，而且不用发布、不用审核。

1. 打开目标群 → 群设置 → **群机器人** → 添加机器人 → **自定义机器人**；
2. 起名「供应链系统告警」，复制它给出的 **Webhook 地址**；
3. 把地址发给我（这是群级地址，不是账号密钥）。

代码侧**早已支持这条路**（`src/jobs/notify.ts`，且会校验必须是飞书官方群机器人 HTTPS 地址），
填入 `FEISHU_WEBHOOK_URL` 即可投产。

#### 路线 B：另建一个最小权限应用

若你更希望走应用机器人（可读群列表、能力更多）：

1. 飞书开放平台 → **新建自建应用**，名字建议「供应链系统通知」；
2. 只申请这 **3 项权限**，一项都不要多：
   - `im:message:send_as_bot`（以机器人身份发消息）
   - `im:chat:readonly`（读取机器人所在群列表）
   - `application:application:self_manage`（读取自身应用信息，供体检用）
3. 开启机器人能力 → 发布版本 → 等审核通过；
4. 把新应用的机器人**拉进「供应链系统告警」群**；
5. 把新的 App ID / App Secret 给我，我来完成配置与复验。

> 不建议继续用「总经办数据应用」：它是公司级的大权限应用，
> 拿它当通知机器人，等于把一把能开全公司飞书的钥匙常驻在供应链服务器上。

> 另外：我建的这个群目前**只有机器人一个成员**。请把赵总和相关负责人拉进去，
> 否则告警发出来没人看得到。

## 2. 用友 —— 网关已找对，缺的是逐条 API 授权

### 实测结论（网关×鉴权变体矩阵，逐条打过真实请求）

**先纠正我自己上一轮的错误判断。** 我曾报告"`c4.yonyoucloud.com` 是登录门户不是业务网关"——
**这是错的**，原因是我当时漏了 `/iuap-api-gateway` 路径，裸 `c4.yonyoucloud.com` 取不到 token，
我据此误判整个域名。跑完网关矩阵后的真实结论：

| 网关 | 能否取 token | 业务调用返回 | 判读 |
|---|---|---|---|
| `https://c4.yonyoucloud.com/iuap-api-gateway` | ✅ | `310037 API未被授权：APPKEY[…]未获得要调用的API[…]的授权` | ✅ **正确网关** |
| `https://api.diwork.com` | ✅ | `310005 应用不存在` | ❌ 另一个集群，本 AppKey 不在其上 |
| `https://c4.yonyoucloud.com`（不带路径） | ❌ 空响应 | — | 路径写漏才会这样 |

**关键差别：** 正确网关给的是 `310037` —— "这个 AppKey **没获得这条 API 的授权**"，
并且**逐条点名了具体接口路径**。这比 `310005 应用不存在` 精确得多：
网关认得这个应用，只是**没把 API 逐条勾给它**。

对正确网关逐条试 8 个契约，当前 **已授权 0/8**（全部 `310037`）。

随时可自查（授权生效后重跑即可看到逐条变绿）：

```bash

```

## 3. 聚水潭 —— 签名正确，缺商家授权

### 实测结论

- 按官方文档实现的签名（`MD5(secret + 排序后的 key+value 拼接 + secret)`）**被服务端接受**；
- 返回：`{"code":130,"msg":"入参缺少access_token"}`。

**判读：** 签名算法和 AppKey/Secret 都对。聚水潭的开放接口是 OAuth 模式——
光有应用凭据不够，还需要**商家（你们的聚水潭账号）授权这个应用**，换出 `access_token`。

### 你需要做的：点一个链接就行

授权链接我已经拼好。签名用的是 `src/server/integrations/jst.ts` 里那份实现——
它**被服务端证明过是对的**：用它调业务接口返回的是 `130 入参缺少access_token`
而不是 `120 验证失败!无效签名`，说明签名这一关过了。链接本身也实测可打开
（渲染出「聚水潭ERP服务授权」登录页；注意这只证明端点可达，真正证明签名的是上面那条 130）。

生成链接：

```bash
npm run jst:auth-url
```

然后：

1. 用**你们的聚水潭账号**打开输出的链接（我不会替你登录，账号口令的事请你自己来）；
2. 点「同意授权」；
3. 跳转后地址栏会带 `code=xxxx`，把 code 发给我，或直接运行：

```bash
npx tsx scripts/jst-exchange-code.ts <code>
```

换到的 `access_token`（和 `refresh_token`，如果有）会自动写进 `.env`，
随后 `npm run readiness` 即可看到聚水潭转为已配置。

> `code` 只有 15 分钟有效，过期就重新跑一次 `npm run jst:auth-url`。
> （`JST_SYNC_ACTOR_ID=1` 已配好。）

## 关于"实测证据"字段

`*_LIVE_VERIFIED_AT` / `*_LIVE_VERIFIED_REF` 这些字段我**没有填**。
它们的作用是记录"这条链路真的跑通过一次真实业务数据"，
系统会校验证据编号必须绑定当前应用+目标对象的指纹，填错或过期会自动阻塞。
在授权真正打通、跑过一轮真实数据之前填这些字段，等于自己骗自己——所以留空。
